# Library Rental

Модуль обліку книг, примірників, читачів і видач.

## Права доступу

### Групи

- **Бібліотекар**: повний доступ до книг, примірників, читачів і видач. Бачить усі видачі.
- **Читач**: може читати книги, примірники та власні видачі. Читачі не можуть створювати, змінювати або видаляти записи; доступу до моделі читачів немає. У меню доступний лише пункт **Мої видачі**.

### Матриця прав

| Модель | Бібліотекар: read/write/create/unlink | Читач: read/write/create/unlink |
| --- | --- | --- |
| `library.book` | 1/1/1/1 | 1/0/0/0 |
| `library.copy` | 1/1/1/1 | 1/0/0/0 |
| `library.member` | 1/1/1/1 | 0/0/0/0 |
| `library.loan` | 1/1/1/1 | 1/0/0/0 |

### Record rules

Для `library.loan` читач бачить видачі, привʼязані до нього одним із двох
способів: через `member_id.user_id` або через `member_id.partner_id`,
який дорівнює контакту поточного користувача:

```python
['|',
 ('member_id.user_id', '=', user.id),
 ('member_id.partner_id', '=', user.partner_id.id)]
```

Бібліотекар бачить усі видачі через правило з доменом `[(1, '=', 1)]`.
В обох правил поле `groups` заповнене явно. Без групи правило стало б
глобальним і могло б замкнути доступ не лише потрібній групі, а всім
користувачам моделі.

Для списку та форми видач читачеві показується related-поле `member_name`,
а `member_id` доступне лише бібліотекарю. Це не вимагає read-доступу читача
до `library.member` під час відображення видачі.

## Звʼязок із контактами

`library.member` повʼязаний із `res.partner` через поле `partner_id`.
Поля `name`, `email` і `phone` читача є related-полями контакту, тому
ці дані зберігаються в контакті та не вводяться двічі. Поле `name` є
збереженим (`store=True`) і доступне для редагування через контакт.

`partner_id` навмисно не має `required=True` на рівні поля: це дозволяє
оновити модуль у базі, де вже існують читачі без контактів, без помилки
`NOT NULL`. Для нових читачів обовʼязковість забезпечується в `create()`:
якщо передано `user_id`, використовується `user.partner_id`; інакше
створюється новий контакт із `name`, `email` і `phone`.

`post_init_hook` проходить наявних читачів без `partner_id`, спочатку шукає
контакт за email, а якщо його немає — створює контакт із даних читача та
привʼязує його. Унікальність `user_id` і `partner_id` захищена SQL
обмеженнями.

На формі контакту бібліотекар бачить smart button **Читач**, якщо контакт
привʼязаний до читача. Кнопка відкриває картку `library.member`.

### Перевірка під демо-Читачем

- **(а)** видно лише меню **Мої видачі**;
- **(б)** у списку відображаються лише видачі цього читача;
- **(в)** прямий URL книги, примірника та чужого читача дає `AccessError`.

## Що довелося виправити вручну після AI-генерації

Реальні ручні правки можна додати до цього списку:

- глобальний rule без `groups`;
- `1,1,1,1` для Читача;
- неправильний порядок у `__manifest__.py`;
- implied_ids Бібліотекар -> Читач;
- `AccessError` на `member_id`;
- адміністратор без групи.

Для звʼязку з контактами:

- `required=True` на `partner_id` ламає оновлення через наявних читачів;
- дублювання `name`, `email` і `phone` у читачі та контакті створює
  неузгоджені дані;
- неузгоджені `partner_id` і `user_id` порушують record rule
  `member_id.user_id`.

## Діагностика порожнього списку

Перевірте користувача, обидва способи привʼязки читача та результат record
rule в Odoo shell:

```python
user = env['res.users'].search([('login', '=', '<логін Читача>')])
env['library.member'].search([('user_id', '=', user.id)])
env['library.member'].search([('partner_id', '=', user.partner_id.id)])
env['library.loan'].with_user(user).search([])
```

- Перший пошук має повернути читача, якщо `library.member.user_id` прямо
  вказує на цього користувача.
- Другий пошук має повернути читача, якщо він привʼязаний через
  `library.member.partner_id` до контакту користувача.
- Останній пошук показує видачі після застосування прав і record rule.
  Порожній результат означає, що жодна видача не відповідає жодному з
  двох способів привʼязки або користувач не має потрібної групи/доступу.

Record rule читача використовує обидва звʼязки:

```python
['|',
 ('member_id.user_id', '=', user.id),
 ('member_id.partner_id', '=', user.partner_id.id)]
```

Action **Мої видачі** не має `domain`, `context`, `default_state` або
`search_default_*`; список фільтрується лише цим record rule. Фільтри
активних, прострочених і повернених видач у search view не активуються
за замовчуванням.

## Практичне заняття 5

### Що згенеровано без правок

- Wizard `library.return.wizard` є `TransientModel`, відкривається модально
  з активної видачі та підтверджує повернення.
- Додано вибір стану примірника, поле нотаток і кнопку **Оформити
  повернення** на формі видачі.
- Додано QWeb PDF-звіт історії видач читача з пунктом у меню Дії/друку.

### Що виправлено вручну/відхилено від шаблона завдання

- У реальній моделі `library.copy` немає поля `condition`. Реальне поле
  називається `state` і має значення `available`, `loaned`, `lost`,
  `damaged`. Wizard використовує саме це поле та його selection без
  дублювання значень; після повернення записується
  `copy_id.state = condition_on_return`.
- `fine_amount` уже обчислюється через
  `@api.depends("due_date", "return_date")`, тому окремий явний виклик
  перерахунку не потрібен.
- Запис повернення виконується з контекстом `library_rental_sync=True`,
  оскільки поточний `library.loan.write()` забороняє прямий запис `state`
  без цього контексту та сам звільняє примірник.
- У кнопці форми використано `id` замість `active_id`: Odoo 19 перевіряє
  expressions у view як поля поточної моделі й відхиляє `active_id`, бо це
  не поле `library.loan`. Значення `id` передає той самий поточний loan.
- Шаблон `report_member_loan_history` створено як обгортку для звіту, а
  `web.external_layout` викликається всередині циклу `docs`, щоб кожен
  читач мав власну сторінку.
- Окрему кнопку звіту на формі читача не додано: звіт привʼязаний до
  `library.member` через `binding_model_id`.

### Результати перевірки Кроку 6

- (а) `action_confirm()` починається з `ensure_one()` і не містить циклу
  по `self`.
- (б) Модель звіту — `library.member`; `report_name` дорівнює
  `library_rental.report_member_loan_history`, а шаблон-обгортка має
  відповідний id.
- (в) Шаблон ітерує `docs` як читачів, а рядки таблиці — як
  `member.loan_ids`.

### Як відтворити сценарій і зробити скріншоти

1. Оновіть модуль `library_rental` у базі даних і увійдіть користувачем із
   групою **Бібліотекар**.
2. Створіть книгу, примірник і читача, потім оформіть активну видачу.
3. Відкрийте активну видачу та зробіть скріншот кнопки **Оформити
   повернення** і модального wizard.
4. Виберіть стан примірника, підтвердьте повернення та зробіть скріншот
   стану `returned`, дати повернення і суми штрафу.
5. Відкрийте читача, у меню Дії/друку виберіть **Історія видач читача** і
   збережіть PDF та скріншот таблиці з кількома видачами.
